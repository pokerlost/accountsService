# Database migrations

This page documents Alembic ownership and migration discipline for the mandatory PostgreSQL database.

## Apply and revert revisions

The Makefile runs Alembic through the locked environment with `PYTHONPATH=app`:

```bash
make db-upgrade
make db-downgrade
```

These commands map to `alembic upgrade head` and `alembic downgrade -1`. They require a valid `ACCOUNTSSERVICE_DATABASE__URL` and a reachable PostgreSQL instance. The application does not run migrations at startup.

## Create a revision

After changing SQLAlchemy metadata, create a focused autogenerated revision:

```bash
make db-revision message=describe_schema_change
```

The target runs `alembic revision --autogenerate -m "describe_schema_change"`. Review the generated upgrade and downgrade operations before applying them; autogeneration reflects detected metadata differences and is not a substitute for migration review.

Run Alembic's metadata comparison explicitly when persistence metadata or revisions change:

```bash
PYTHONPATH=app uv run --locked alembic check
```

## Metadata ownership

`alembic/env.py` uses the shared `Base.metadata`. Import every concrete `*Model` through `persistence.database.models` so its table is registered before Alembic compares metadata. Keep model imports in that registration facade rather than adding migration-only imports.

Historical revisions created account, password-credential and resumable-workflow tables. The
current runtime metadata contains no corresponding ORM models. Revision
`20260903_0003` removes obsolete authorization classifications and changes planned remote workflow
intent to exact scope arrays. It preserves status-only synchronization rows and rejects an upgrade
when provisioning or classification-mutation rows cannot be translated without guessing
authService-owned grants. Operators must resolve those rows before retrying the historical migration.
Do not run autogenerate from the empty foundation metadata or infer that a table should be dropped.

Add or change a model and migration only for a responsibility defined in `SERVICE.md`; never edit
an already applied revision to represent a later schema change. Use a forward migration for every
later schema transition.

For transaction behavior at runtime, see
`docs/architecture/persistence-and-transactions.md`.
